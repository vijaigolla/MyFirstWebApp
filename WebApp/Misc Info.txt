Understanding endpoints in ASP.Net Core: (A terminal middleware that short-circuits the flow and returns a response to the client)
1. An endpoint is a piece of code that can handle an HTTP request and generate an HTTP response
2. Endpoints are defined using the app.Map, app.MapWhen, or app.Use methods in the Configure method of the Startup class
3. Endpoints can be associated with a specific HTTP method (GET, POST, PUT, DELETE, etc.) and a specific route pattern using MapGet, MapPost, MapPut, MapDelete, and more
4. Endpoints can be used to implement RESTful APIs, MVC controllers, Razor Pages, gRPC services, and more
5. Endpoints can be decorated with attributes such as [HttpGet], [HttpPost], [Route], [Authorize], and more to specify their behavior and requirements
6. Endpoints defined using app.UseWhen or app.MapWhen can be used to conditionally execute middleware based on a predicate function that evaluates the HttpContext, allowing for more complex routing scenarios and dynamic endpoint selection based on request characteristics. 
   But the endpoints defined using app.UseWhen or app.MapWhen are not terminal middleware and do not short-circuit the flow, allowing for further processing of the request by subsequent middleware components in the pipeline.
7. Endpoints that are not terminal middleware can be used to implement middleware components that perform additional processing on the request or response, such as logging, caching, compression, or authentication, before passing the request to the next middleware component in the pipeline.

Types of endpoints in ASP.Net Core:
The types of endpoints in ASP.Net Core include:
1. Minimal API endpoints: These are endpoints defined using the app.MapGet, app.MapPost, app.MapPut, app.MapDelete, and other similar methods in the Configure method of the Startup class. They are typically used to implement lightweight APIs with minimal overhead and can be used to handle simple requests and responses.
2. MVC controller endpoints: These are endpoints defined using the [HttpGet], [HttpPost], [HttpPut], [HttpDelete], and other similar attributes on controller action methods. They are typically used to implement more complex APIs with full-featured routing, model binding, and validation capabilities.
3. Razor Pages endpoints: These are endpoints defined using the @page directive in Razor Pages. They are typically used to implement web pages with server-side rendering and can be used to handle both GET and POST requests.
4. gRPC service endpoints: These are endpoints defined using the gRPC framework in ASP.Net Core. They are typically used to implement high-performance, low-latency APIs that can handle large volumes of requests and responses.
5. SignalR hub endpoints: These are endpoints defined using the SignalR framework in ASP.Net Core. They are typically used to implement real-time web applications that can handle bi-directional communication between clients and servers.


Endpoints vs Terminal Middleware:
Endpoints are specific handlers for requests that are defined using the app.Map, app.MapWhen, or app.Use methods in the Configure method of the Startup class. 
They can be associated with a specific HTTP method and route pattern, and can be used to implement RESTful APIs, MVC controllers, Razor Pages, gRPC services, and more. Endpoints can also be decorated with attributes to specify their behavior and requirements.

Terminal middleware, on the other hand, is a middleware component that short-circuits the flow of the request and returns a response to the client.
It is typically used to handle requests that do not match any defined endpoints or to provide a default response for unhandled requests. 
Terminal middleware can be defined using the app.Run method or by returning a response from an endpoint.

In summary, while endpoints are specific handlers for requests, terminal middleware serves as a last resort to process requests that do not match any defined endpoints.

Where the Functions OverlapThe overlap happens because both serve as the ultimate request handler—their primary job is to generate an HTTP response and short-circuit the pipeline so no further down-stream logic executes.Under the hood,
modern Endpoints are actually executed by a specialized Terminal Middleware.In modern .NET Core (.NET 6+),
the pipeline sets up an implicit structure:UseRouting() matches the incoming URL to an Endpoint object.Custom middlewares run (and can inspect what endpoint was matched).UseEndpoints() / EndpointMiddleware acts as a Terminal Middleware. 
It grabs the matched endpoint and executes its handler, short-circuiting the request back up the chain.Code Example of OverlapYou can achieve the exact same functional outcome (returning text on a specific route) using either approach:

// 1. Using Terminal Middleware
app.Use(async (context, next) => {
    if (context.Request.Path == "/old-way") {
        await context.Response.WriteAsync("Hello from Terminal Middleware!");
        return; // Short-circuiting explicitly by NOT calling await next()
    }
    await next();
});

// 2. Using an Endpoint
app.MapGet("/new-way", async (context) => {
    await context.Response.WriteAsync("Hello from an Endpoint!");
}); // Under the hood, this compiles into an endpoint handled by EndpointMiddleware

Deep Dive: Each Middleware Component Explained
1. Exception Handler / Developer Exception Page (app.UseExceptionHandler() / app.UseDeveloperExceptionPage())
·Why it's first: It must be placed at the very beginning of the pipeline so it wraps all subsequent middleware.
·Role: When the request moves forward, this middleware does nothing but open a try/catch block. If any middleware downstream throws an unhandled exception, the request short-circuits, and control flows backward directly into this component to log the error and return a friendly error page or an RFC 7807 Problem Details response.
2. HSTS (app.UseHsts())
·Why it's here: It must run early, but only on secure connections where no error has disrupted the response header layout.
·Role: Adds the Strict-Transport-Security header to the HTTP response. This forces browsers to always interact with your site using HTTPS for subsequent requests, preventing man-in-the-middle attacks.
3. HTTPS Redirection (app.UseHttpsRedirection())
·Why it's here: It sits right before asset delivery to block unencrypted requests.
·Role: Checks incoming traffic. If a user hits your app via http://, this middleware intercepts it, issues an HTTP 307/301 redirect status code, and forces the browser to reload the page via https://.
4. Static Files (app.UseStaticFiles())
·Why it's here: It is positioned before routing, authentication, and authorization for performance optimization.
·Role: If the incoming URL matches a physical asset inside your wwwroot folder (like image.png, site.css, or app.js), this middleware acts as Terminal Middleware. It directly reads the file off the disk, writes it to the response stream, and returns it to the browser. By putting it here, your server completely avoids wasting CPU cycles on routing or database authorization checks for public images and styles.
5. Routing (app.UseRouting())
·Why it's here: It must run before any middleware that relies on route logic (like CORS configurations or Authorization rules).
·Role: This middleware parses the requested URL path and inspects your application's defined endpoints (like Controllers or Minimal API maps). It selects a matching endpoint and attaches it directly to the request's context (HttpContext.GetEndpoint()). Crucially, it does not execute the route handler yet; it simply assigns it.
6. CORS (app.UseCors())
·Why it's here: It must follow UseRouting because modern CORS policies can be evaluated on a per-endpoint basis using attributes like [EnableCors].
·Role: Appends Cross-Origin Resource Sharing headers to the response, establishing which external domains, HTTP methods, and request headers are legally allowed to interact with your API from a browser context.
7. Authentication (app.UseAuthentication())
·Why it's here: It must figure out who the user is before the pipeline tries to determine what they are allowed to do.
·Role: Inspects the request for a credential payload (like a JWT Bearer token in the Authorization header or a session Cookie). If found, it populates the HttpContext.User property with a ClaimsPrincipal identity object.
8. Authorization (app.UseAuthorization())
·Why it's here: It relies directly on the identity established by UseAuthentication and the route target identified by UseRouting.
·Role: Compares the ClaimsPrincipal on the request against the security metadata attached to the target endpoint. If the endpoint requires a role or policy that the user lacks, this middleware short-circuits the pipeline immediately and returns an HTTP 401 Unauthorized or HTTP 403 Forbidden status.
9. Custom Middleware (app.Use(...) / app.UseMiddleware<T>())
·Why it's here: By placing custom logic after Authorization, you guarantee that your business logic code only executes for verified, legitimate traffic.
·Role: This is where you insert custom logging, request-correlation IDs, localization adjustments, multi-tenant database connection setting, or custom request sanitization.
10. Endpoint Middleware (app.MapControllers() / app.MapGet() / app.UseEndpoints())
·Why it's last: This is the core engine of your software application.
·Role: It acts as the ultimate Terminal Middleware. It reads the endpoint selection made back in step 5 (UseRouting), executes the underlying action method, Razor Page handler, or Minimal API delegate, and serializes your data models into JSON or HTML to generate the final HTTP response payload.

Router:
router is a terminal middleware that short-circuits the flow and returns a response to the client
Routing is the process of mapping an incoming HTTP request to a specific endpoint based on the request's URL and HTTP method
404 Not Found is returned when no matching endpoint is found for the incoming request by using the 404 middleware or by returning a NotFound result from an endpoint

Required Root Parameters:
The required root parameters for an HTTP request are the method, URL, and version. 
The method specifies the type of request being made (e.g., GET, POST, PUT, DELETE), 
the URL specifies the resource being requested, and the version specifies the HTTP version being used (e.g., HTTP/1.1, HTTP/2).
An example of a required root parameter for an HTTP request is: GET /api/employees/123 HTTP/1.1
Route templates are used to define the structure of the URL and can include parameters that are extracted from the URL and passed to the endpoint for processing.
An example of a route template is: /api/employees/{id}, where {id} is a parameter that can be extracted from the URL and passed to the endpoint for processing.
The literal segments of the route template are the parts of the URL that are fixed and do not change, while the parameter segments are the parts of the URL that can vary and are extracted from the URL and passed to the endpoint for processing.
The literal segments of the route template are used to match the incoming request's URL, while the parameter segments are used to extract values from the URL and pass them to the endpoint for processing.They are not case sensitive and can be used to define the structure of the URL and extract values from the URL for processing by the endpoint.
optional parameters in route templates are parameters that may or may not be present in the URL and can be specified using a question mark (?) after the parameter name.
for example, /api/employees/{id?} is a route template that defines an optional parameter {id}, which may or may not be present in the URL. If the parameter is not present, the endpoint can still be invoked without it.
Multiple optional parameters can be defined in a route template by specifying multiple parameters with question marks (?) after their names. The order of the parameters in the route template matters, as it determines how the URL is matched and how the values are extracted from the URL for processing by the endpoint.
You cannot have required parameters after optional parameters in a route template, as it would create ambiguity in how the URL is matched and how the values are extracted from the URL for processing by the endpoint.
You can get the route parameters from the HttpContext.Request.RouteValues property, which is a dictionary that contains the values of the parameters extracted from the URL based on the route template.
Default values for route parameters can be specified in the route template using the equals sign (=) after the parameter name. For example, /api/employees/{id=1} is a route template that defines a default value of 1 for the {id} parameter. If the parameter is not present in the URL, the default value will be used when invoking the endpoint.
Parameters can be constrained in route templates using constraints, which are specified after the parameter name using a colon (:). For example, /api/employees/{id:int} is a route template that defines a constraint that the {id} parameter must be an integer. If the value extracted from the URL does not match the constraint, the endpoint will not be invoked.
Types of constraints that can be used in route templates include int, bool, datetime, decimal, double, float, guid, long, short, string, and more. Custom constraints can also be defined by implementing the IRouteConstraint interface.
An example IrouteConstraint implementation is a class that checks if a parameter value is a valid email address. The class can implement the IRouteConstraint interface and define the Match method to check if the parameter value matches the email address format. If the value does not match, the endpoint will not be invoked.

Model Binding in ASP.Net Core:
Model binding is the process of mapping HTTP request data to action method parameters or properties of a model object. 
It automatically maps data from the request (such as query string values, form data, or route values) to the parameters of an action method or the properties of a model object. 
This simplifies the process of working with request data in ASP.NET Core applications.
.NET core model binding supports various data sources, including query strings, form data, route values, headers, and more.
How does it do it? 
It uses a set of built-in model binders that are responsible for extracting data from the request and converting it to the appropriate type.
For example, the DefaultModelBinder is responsible for binding simple types (such as int, string, bool) from the request data to action method parameters or model properties.
First it looks for the value in the route values, then in the query string, and finally in the form data. If it finds a matching value, it converts it to the appropriate type and assigns it to the parameter or property.
if not found, it will use the default value for the parameter or property type (e.g., 0 for int, null for reference types).

Body can be used for complex types, such as objects or collections, and can be sent in various formats, such as JSON or XML, for verbs like POST, PUT, PATCH, and DELETE. 
The model binder will deserialize the request body into the appropriate type based on the Content-Type header of the request.
For minimal APIs, model binding can be done using the [FromBody], [FromQuery], [FromRoute], [FromHeader], and [FromForm] attributes to specify the source of the data for each parameter.
However, for complex types, the [FromBody] attribute is typically used to indicate that the data should be bound from the request body.
Another restrction for minimal APIs is that only one parameter can be bound from the request body, as the body can only be read once. If multiple parameters need to be bound from the body, a single complex type can be used to encapsulate the data.
Also, for minimalAPI's the body format is typically JSON, and the model binder will use the System.Text.Json serializer to deserialize the request body into the appropriate type.

Use BindAsync method to bind the request body to a complex type asynchronously. This method reads the request body and deserializes it into the specified type, allowing for more efficient handling of large request bodies.
for example, you can define a complex type called Employee and use the BindAsync method to bind the request body to an instance of the Employee class. The method will read the request body, deserialize it into an Employee object, and return it for further processing in the action method.
Syntax for BindAsync method is as follows:
Employee employee = await context.Request.BindAsync<Employee>();

Some times we have to combine typedresults and results to return a response that includes both strongly typed data and additional metadata or headers.
